# telegram-library: notes for developers

The plugin's sources are ES modules under `src/`. `scripts/build.mjs` bundles them into the single file Kino loads: `npm run build` writes `plugin.js` (the published entry, committed; a test fails when it is stale). Tests run with `node --test`: `npm test` builds, then runs `test/`. No test reaches the network.

## Layout

- `src/mtproto/`: the MTProto client.
  - Transport, auth key and session.
  - `client.js`: the bot login, `getFile` (a file's chunks, or with `thumbSize` one of its thumbnails), and `call`.
  - `requests.js`: the serialized methods, plus `ALLOWED_CALLS`, the one frozen list of what `call` may send.
  - `schema/reader.js` + `schema/generated.js`: the schema-driven TL reader. Regenerate with `node scripts/gen-schema.mjs`; a test fails when `generated.js` is stale.
  - `discovery.js`: the video index built from the bot's update boxes.
- `src/plugin.js`: the entry, Kino's exports (`home`, `search`, `browse`, `resolve`, `read`, `image`, `details`, `section`, `categories`, `settingsStatus`, `action`, `validateSettings`).
- `src/shell/`: the plugin around the client.
  - `live.js`: the settings, the one live client per runtime, the stored session (`tg.session`), the login once per device.
  - `library.js`: channel slots and toggles, the refresh (discovery -> `kino.catalog`), purges, and every list Kino shows.
  - `read.js`: the byteSource `read`; `b64.js`: hex to base64 natively (AES-CTR twice).
  - `enrich.js`: names and TMDB: `parseName` (file name and caption to `{ title, year?, type, season?, episode?, tmdbId? }`), the `kino.meta` query, the answer kept in the row, and the bounded pass a refresh runs.
  - `image.js`: the imageSource `image` export (Telegram's thumbnail of a video TMDB has no poster for).
  - `errors.js`: every failure as a `kino.error` with a sentence for the person; `text.js`: every text, Spanish and English.
  - `store.js`: the `kino.storage` keys.
- `testkit/`: the test-only pieces.
  - `fake-dc.mjs`: the fake Telegram DC.
  - `fake-world.mjs`: channels and private chats for the discovery.
  - `tl-serializer.mjs`: an independent TL writer, so the fixtures never share code with the reader.
  - `plugin-harness.mjs`: the whole plugin as Kino runs it: the bundle in the kit's sandbox on the kit's `kino`, settings per runtime, one storage and catalog per "device". It swaps one line of the bundle, the RSA keys, for the fake cluster's.

## Discovery: what to know

- **Where the data comes from.** Bots cannot list dialogs or read history; `messages.getHistory` answers `BOT_METHOD_INVALID`. So everything comes from `updates.getDifference`, which starts at pts 1 on the first run, and from `updates.getChannelDifference` per known channel. A channel becomes known only when it appears in a `chats` vector.
- **The `differenceTooLong` gap is skipped.** After `updates.differenceTooLong`, the common box jumps to a fresh `updates.getState`. Known channels are rescanned from pts 1, so their videos are not lost. Two things are lost:
  - A channel the bot joined during the gap appears only with its next post, or with another update that names it.
  - Private-chat videos sent during the gap are lost.
- **Storage.** The update state and the index are saved together under the key `tg.discovery`.
  - The saved value never exceeds `budgetBytes`, which defaults to 160 000 so the client's own keys keep room under Kino's 256 KB. Pass a larger value when the plugin has a larger quota.
  - When the index does not fit, the oldest entries are left out of the saved copy, and the result has `truncated: true`.
  - A write the store refuses never throws. The result has `persisted: false`, and the same runtime goes on from its in-memory state.
- **Isolated failures.** A channel whose answer cannot be parsed, or that answers an rpc error, is reported in `errors` and keeps its pts; the other channels go on. A failed common-box answer keeps the common state, and the channels are still scanned. `FLOOD_WAIT` stops the scan, keeps the progress, and is surfaced as `floodWait`.
- **Adding a method for the shell.** Write its serializer in `requests.js` and add its constructor id to `ALLOWED_CALLS`. `client.call` refuses everything else before sending: auth methods, invoke wrappers, `gzip_packed`, `msg_container`, and destructive methods.

## The plugin shell: what to know

- **Index.** The discovery runs with `persistEntries: false`: `tg.discovery` holds only the update state, and each refresh's `changes` go to `kino.catalog` (upsert in batches of 500, removals by id). A catalog row is `{ id: "<chat>:<msg>", title, sort: <message date>, data: { chatId, msgId, size, mime, duration, width, height, caption, doc: { id, accessHash, fileReference (hex), dcId }, n: <parsed name>, pk: <lookup key>, th?: { t: <thumb type>, s: <bytes> }, tm?: <TMDB answer or miss>, file? } }`, about 350 to 650 bytes of `data` (the catalog allows 4 096). The catalog `title` joins every name the video goes by (TMDB's title, the parsed name, the file's base name, " / " between them) so a search finds any of them; cards show `displayTitle` (TMDB's title, else the parsed name, plus SxxExx for an episode).
- **Refresh policy.** From `home()` and the `refresh` action only, never from `search()`. At most every 5 minutes, unless a pass is unfinished or a toggle changed; a FLOOD_WAIT blocks it until the wait is over. A failure keeps the old rows and is stored as `tg.shell.error` (shown as a notice row and in the status line).
- **Channels.** Slots 1 to 8 are stable and first-seen (`assignSlots`): the discovery gives each new channel `seen` (one more than the highest so far), a new channel takes the next free slot, and only slot 1's toggle defaults on. Anyone can add the bot to their own channel, so a newcomer must never shift the owner's channel or inherit a switched-on slot. A lost channel keeps its slot, shown "(the bot lost access)" (`shell.missing`), never reused; channels past 8 are counted in the status line. Known limit: channels first met in the same batch (a fresh install of a bot already in several channels) are ordered by update order, which Telegram does not promise is the same on every device. Slot N follows the `chN` toggle. A channel off is never scanned and has no rows: turning it off queues a purge (ids `<chat>:<top>` down to 1, 500 per remove call, 40 calls per step); turning it on calls `discovery.resetChannel` (read again from pts 1). Private chats and groups are ignored: anyone can message a bot.
- **Rows without a channel filter.** `kino.catalog` searches titles only, so a channel's newest videos are read with `kino.catalog.get` over message ids from the channel's highest one down (500 ids per call, 10 calls at most).
- **The read hot path.** `getFile(..., { hex: true })` slices the file bytes out of the decrypted hex; `b64.js` turns hex into base64 with two native `aes-128-ctr` passes (CTR twice with the same key and counter is the identity). The JavaScript passes left over a 1 MiB chunk are upstream of the shell: the app's prelude decoding the WebSocket frame into a Uint8Array, and the transport's one `toHex` of it.
- **Secrets.** The three settings are read with `kino.config.get` (they are `password` settings; Kino's sealed `secrets` are an author's values bound to a repository, not the person's, and a sealed marker is only swapped inside `kino.fetch`). They are never logged, never stored, never part of an error: `tg.session`'s `fp` is a 16-hex-digit SHA-256 prefix of the api_id and the token. `test/plugin.test.mjs` scans storage, catalog, logs, errors and answers for them.
- **Sealed session.** `tg.session` is `{ v: 2, fp, device, salt, iv, ct }`: the client's `exportState()` as AES-256-GCM (`kino.crypto.encrypt`) under `HMAC-SHA256(key = api_hash + "\n" + bot token, data = "tg.session\n" + salt)`, the salt random per install (kept while the session lives). Kino gives a plugin no Keystore of its own, so this is what keeps an auth key out of a plain `kino.storage` dump or backup. A changed token or api_hash, or a damaged or tampered value, opens to nothing: a new key and one budgeted login. A v1 (0.2.2, plaintext) value is read once and rewritten sealed. `testkit/session-open.mjs` opens it in tests.
- **Logins that must wait.** A login refused (`token_invalid`, `api_id_invalid`) or delayed (`flood_wait`, the device's own `login_budget`) is stored as `tg.login` (`{ fp, kind, until? }`); `open()` checks it before every login, so a read or a refresh retried during a FLOOD_WAIT sends no other `importBotAuthorization`, in this runtime or a fresh one. `image()` connects with `noLogin`: no stored login, no picture, no login.
- **Device mark.** `checkDevice()` (live.js) runs before anything reads `kino.storage`: the stored session must carry the id of the catalog's `~device` row, else session, update state and shell state are dropped and the catalog rebuilt. The mark is a catalog row (title `~`, sort 0): `countVideos()` leaves it out, and no list shows it (it belongs to no channel).
- **Concurrency.** One `connect` in flight per runtime (shared promise, cleared on failure) and one `refresh` (a second caller gets the running one's answer). `withSession` re-logs in once (budgeted) when the session died (`auth_key_unregistered`); AUTH_KEY_DUPLICATED/INVALID drop that DC's key in the client.
- **Commit order.** The discovery runs with `commit: false`; the shell writes the catalog, then calls `commit()`. A refresh stops at 14 s from its start (`deadline`) and goes on next time; a read keeps all its requests inside 17 s.
- **Memory model (`src/mtproto/big.js`).** A hand-kept model, not the QuickJS heap: `big.hold(n)`/`big.release(n)` at every place the transport, the session, the client cache and `read` make or drop a big string. Tests bound its peak (two copies of a 3 MiB packet) and check it returns to 0 after every kind of read; that catches a missing release in our code, never a reference kept by mistake that nobody declared, nor the copies inside `kino.crypto`/`kino.ws`.
- **Incoming checks** (`session.js` `openPacket`). auth_key_id, msg_key (a `crypto_error` from `aesIgeVerify`, whatever its message, is the same `protocol` "msg_key mismatch"), session id, padding 12 to 1024 bytes, an odd server msg_id, and duplicates (the last 512 server ids; a repeat is dropped and logged). Not checked: the msg_id's time window against the local clock (the client keeps the server's offset; a cheap check would refuse answers on a device whose clock is far off). `new_session_created` resends every waiting request sent before its `first_msg_id`.
- **Key exchange bounds.** `createAuthKey` runs under one deadline (`timeoutMs` from its start): each `plainCall` waits only for what is left. `factorPq` refuses a pq outside 4 to 2^64 and gives up after 2^22 Pollard steps.
- **Untrusted text.** Channel titles, file names and captions come from anyone who can post where the bot is: `clean.js` replaces C0/C1 controls and bidi marks and overrides (U+200E/F, U+202A-202E, U+2066-2069) with spaces before any parsing or display.
- **Home's budget.** `homeRows` stops adding channel rows once 17 s (by `kino.now` when Kino has it) passed since `home()` began, logging "home: channel rows skipped, out of time"; the recent row is always there.
- **Native ops, feature-detected (Kino apiVersion 13).** `session.decrypt` uses `kino.crypto.aesIgeVerify` (AES-IGE decrypt + the msg_key SHA-256 check in one native call: `macPrefix` = auth_key bytes 96-128, `macOffset` 8, `mac` = the msg_key; "the mac doesn't match" becomes `protocol` "msg_key mismatch") and `b64.js` uses `kino.crypto.convert(hex, "hex", "base64")`. Each is detected with `typeof kino.crypto.<op> === "function"`; an older Kino gets the previous code (aesIge + sha256, two CTR passes), so the plugin works on both, at full speed only with the ops.
- **Retention between plays.** Kino gives no "stream closed" hook and its QuickJS runtime lives between plays, so a finished play must leave little behind. The read-ahead cache is hard-capped at 2 tracked chunks (`MAX_AHEAD`, about 4 MiB of hex), with a byte bound as a second guard; and `read` calls `idleReset` at its start, which, when no read ran for 20 s, drops the cache and the open connection (the next read reconnects with the stored key). `big.js` sees these, but not QuickJS's own non-refcounted garbage: the real check is a device run.
- **In flight.** At most 3 **chunk** requests per connection at every send (the limit covers `getFile` and its read-ahead only; `call()` and `authorize()` bypass it, they are small and rare): a chunk request waits (up to 2.5 s) for room, and when the room does not come (requests that never answer) the connection is dropped and a new one is opened with the stored key. Abandoned requests count until their answer arrives or `abandonedMs` (30 s) passes.
- **Side effects of `abandon`** (a read that is not the file's last chunk gives up the read-aheads it does not want): an mp4 whose `moov` is bigger than 1 MiB makes Kino read more than one chunk at the end, so the second of those reads abandons the read-aheads of chunks 1-2 started after chunk 0; a read that is not at a MiB offset, or that is split into several requests, wants no read-ahead and so abandons every read-ahead of the file.

## Names, TMDB and pictures: what to know

- **Parsing** (`parseName`, `test/enrich.test.mjs` has the table). Extension, id markers, URLs, bracketed groups, dots and underscores go; a year is a standalone 19xx/20xx token with text before it (the last one wins, never past next year); SxxExx, TxEx, NxNN and "Temporada N Capítulo N" make a series and cut the title there; the first release tag after the first word cuts the rest (resolutions, sources, codecs, audio, languages, editions). Title Case only when the name was all lower or all upper case. A caption marker wins over a file-name marker; the caption's first line names a video whose file name is missing or a camera's (`VID_...`, `IMG_...`, `video`).
- **The switch.** The `tmdb` toggle (default on). Off: no `kino.meta` call at all, and rows already enriched are shown without their TMDB data (`viewOf`), so no TMDB poster URL leaves either; Telegram's thumbnails still show.
- **Lookups** (`enrichStep`). Only inside a refresh (Home or *Actualizar ahora*), after the discovery, also on the early return when the index is recent; never from `search`, `browse`, `read` or `image`. Newest rows first from a cursor in `tg.shell.en` (reset when new rows arrive; a finished walk starts over at most daily, to retry expired misses). At most 4 `kino.meta` calls per pass, none started after 6 s of the pass or when 8 s (Kino's cap for one call) would end past 18 s from the start of the call. `rate_limited`, `unavailable` or any other failure stops the pass and marks nothing; `null` is a miss kept 14 days; `invalid_request` is a miss. By id when a marker gave one, else by title (and year) only where `kino.meta.byTitle` is true (Kino 0.9.55+): on an older Kino a title is left unmarked, so a newer one asks.
- **Keeping answers.** A discovery edit or a refetched file reference rebuilds the row; `carry` keeps the old TMDB answer while the lookup key (`pk`: type and id, or type, lowercase title and year) is the same, so only an edit that changes the name or adds a marker asks again.
- **Thumbnails.** The discovery reads `PhotoSize` (it used to skip it): `thumbOf` keeps one downloadable `photoSize` (or a progressive one's largest step) of at most 256 KB, `m` first, then `x`, then `s`, then the largest; stripped, cached and path sizes are never used. `image({ handle: "t:<row id>" })` checks the row (its channel must be on), refuses without a stored login (no login is ever spent for a picture), then one `upload.getFile(InputDocumentFileLocation{..., thumb_size}, 0, 262144)` through the live client: same serial queue and 3-in-flight rule as the reads, no read-ahead, 8 s of Kino's 10. `FILE_REFERENCE_EXPIRED` refetches the message once; `LOCATION_INVALID` is `not_found`; an answer that is not a JPEG or reaches 256 KB is refused. Kino caches each picture per plugin version and handle, so a handle is asked once.
